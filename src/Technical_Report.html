Section 01

System Overview

Sprint 3 evolves the flat, single-class transaction system of Sprint 2 into a fully structured object-oriented model. The system models a real bank: customers open typed accounts, queue financial transactions, and receive reliable outcomes through a structured validate → execute → commit/rollback lifecycle — all distributed across well-defined, cohesive classes.

The system is intentionally single-threaded and in-memory, keeping the focus on correctness, encapsulation, and clean design rather than concurrency or persistence.

Section 02

Object-Oriented Design Principles

🔒

Encapsulation

All fields in Account, Customer, and Transaction are private or protected. State is accessed through controlled getters and mutated only through validated methods such as deposit(), withdraw(), and execute(). The only exception is forceSetBalance(), which is package-private and used exclusively by the rollback mechanism.

🎭

Abstraction

Both Account and Customer are abstract classes that define a contract (interface) for their subtypes without exposing implementation details. Callers in Bank work against the abstract type — they deposit into an Account, not a SavingsAccount.

🧬

Inheritance

GeneralAccount, SavingsAccount, and DailyAccount all extend Account, inheriting common logic (deposit, balance tracking) while overriding withdraw() and applyInterest() with type-specific rules. Similarly, IndividualCustomer, BusinessCustomer, and HybridCustomer extend Customer.

🔄

Single Responsibility

Each class has exactly one reason to change: Account manages balance rules, Transaction manages the operation lifecycle, Bank manages orchestration, BankCLI manages only user input/output.

Section 06

Transaction Lifecycle

Every transaction goes through a strict four-stage lifecycle. Each stage is delegated to a method on the Transaction object itself — there is no external switch statement or manual balance manipulation outside the class.

Stage 1 Enqueue
→
Stage 2 Validate
→
Stage 3a Execute → Commit
|
Stage 3b Rollback
StageWhat happensStatus after
Enqueue Bank creates a Transaction object and adds it to the FIFO queue. No balance changes. PENDING
Validate validate() checks: amount > 0, accounts exist, no self-transfer, sufficient balance for withdrawals/transfers. PENDING (or ROLLED_BACK if invalid)
Execute → Commit execute() saves balance snapshots, then calls deposit()/withdraw() on the account(s). If no exception is thrown, status becomes COMMITTED. COMMITTED
Rollback On any failure (validation or runtime exception), rollback() restores balances from the saved snapshots and marks the transaction ROLLED_BACK. ROLLED_BACK

Section 07

Key Code Listings

Account.java — Abstract base class

public abstract class Account {
    private final String accountId;
    protected double balance;
    protected final double interestRate;

    public void deposit(double amount) {
        if (amount <= 0) throw new IllegalArgumentException("Amount must be positive");
        balance += amount;
    }

    public void withdraw(double amount) {
        if (amount <= 0) throw new IllegalArgumentException("Amount must be positive");
        if (amount > balance) throw new IllegalStateException("Insufficient funds");
        balance -= amount;
    }

    public abstract void applyInterest();  // overridden per account type
    public abstract String getAccountType();
}

SavingsAccount.java — Minimum balance override

public class SavingsAccount extends Account {
    private static final double MIN_BALANCE = 100.0;

    @Override
    public void withdraw(double amount) {
        if (balance - amount < MIN_BALANCE)
            throw new IllegalStateException(
                "Would breach minimum balance of $" + MIN_BALANCE);
        super.withdraw(amount);  // delegate to parent
    }
}

Transaction.java — validate / execute / rollback lifecycle

public boolean validate() {
    if (amount <= 0) { failureReason = "Amount must be positive"; return false; }
    if (fromAccount == null) { failureReason = "Source account not found"; return false; }
    // ... additional checks ...
    return true;
}

public void execute() {
    savedFromBalance = fromAccount.getBalance();  // save snapshot first
    savedToBalance   = (toAccount != null) ? toAccount.getBalance() : 0.0;
    try {
        switch (type) {
            case DEPOSIT:  fromAccount.deposit(amount); break;
            case WITHDRAW: fromAccount.withdraw(amount); break;
            case TRANSFER: fromAccount.withdraw(amount); toAccount.deposit(amount); break;
        }
        status = TransactionStatus.COMMITTED;
    } catch (Exception ex) {
        failureReason = ex.getMessage();
        rollback();  // automatic on any runtime failure
    }
}

public void rollback() {
    if (fromAccount != null) fromAccount.forceSetBalance(savedFromBalance);
    if (toAccount   != null) toAccount.forceSetBalance(savedToBalance);
    status = TransactionStatus.ROLLED_BACK;
}

Bank.java — processTransaction orchestration

private void processTransaction(Transaction t) {
    if (!t.validate()) {
        t.rollback();
        // log: validation failed
        return;
    }
    t.execute();
    if (t.getStatus() == TransactionStatus.COMMITTED) {
        // log: success + new balances
    } else {
        // log: runtime failure → already rolled back inside execute()
    }
}

Scenario: Transfer with Insufficient Funds

Login as bob. Attempt to transfer $1,000 from the Daily account (balance: $300). Expected: validate() returns false → rollback() is called → balance unchanged → ROLLED_BACK status logged.

Scenario: Savings Minimum Balance Breach

Login as alice. Withdraw $450 from her Savings account (balance: $500, min: $100). This leaves $50 which is below the minimum. Expected: SavingsAccount.withdraw() throws IllegalStateException → caught in Transaction.execute() → rollback() fires → balance stays $500.

Scenario: Daily Withdrawal Limit

Login as bob. Make two withdrawals: $300 then $250. The first succeeds. The second is blocked because $300 + $250 = $550 > DAILY_LIMIT ($500). Expected: second transaction ROLLED_BACK with limit-exceeded message.

Scenario: Successful Transfer

Login as acme (balance: $5,000). Transfer $2,000 to alice's General account. Expected: both balances updated atomically — Acme: $3,000, Alice: $3,000. Both shown in the COMMITTED output.
